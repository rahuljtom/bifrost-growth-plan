AI Model Exit Plan

I drafted this as the asset at the centre of my growth plan. A team fills it in once, then tests it every quarter. It answers one question for the board, the auditor and the platform team: if a model we depend on disappears, what happens, and how fast?

Open template, free to reuse. It maps to regulations but doesn't certify compliance. Have your counsel review it.

Step 2

Name the exit triggers

  • Retirement: the provider deprecates the model. Sarvam deprecated sarvam-m in 2026 v.
  • Access restriction: legal or jurisdictional limits. In June 2026 Anthropic withdrew two models after a US directive r.
  • Price: cost per request rises above a set ceiling.
  • Quality drift: the eval pass rate drops below the threshold in Step 3.
  • Outage: the provider fails for longer than the tolerable outage in Step 1.

Step 3

Name a fallback for each workflow, and set its pass bar

WorkflowFallback 1Fallback 2Eval setPass threshold
Customer-support assistantsame model, India regionanother vendor200 real tickets≥ 90% of primary's score

A fallback that has never passed your own eval set isn't a fallback. It's a hope.

Step 4

Write the switch runbook

  1. Automatic: the gateway retries and fails over on provider errors, with no code change.
  2. Manual: the on-call engineer moves the primary to Fallback 1 in gateway config, not in application code.
  3. Tell the business owner and log the event with time, cause and the model that served traffic.
  4. Re-run the eval set on the serving model within 24 hours.
  5. Review the trigger and update this plan.

Step 5

Test it every quarter, and keep the evidence

  • Run the eval set through every fallback, and record pass or fail against the threshold.
  • Run one live failover drill in staging, and record time to recover.
  • Keep request logs that show which model served each request, by team.
  • Proposed tool: bifrost exit-test would do the first item automatically and export the report a.

Appendix

Implementing Step 4 in Bifrost

Bifrost accepts an ordered fallbacks list on each request and reports which provider served it in extra_fields.routing_info v docs. Model names below are placeholders.

# one request, four layers of protection
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "anthropic/<claude-model>",
    "messages": [{"role": "user", "content": "..."}],
    "fallbacks": [
      "bedrock/<claude-model, India region>",
      "openai/<gpt-model>",
      "sarvam/sarvam-105b"
    ]
  }'
  • Per-team allowlists and budgets: issue each team a virtual key limited to approved models, with a hard budget. My own test returned a 402 once a budget was spent v.
  • Evidence: Bifrost's request logs record the provider that served each call. Enterprise adds audit logs, SSO and RBAC v docs.
  • Measured: on my laptop with mock providers, failover answered in 32 ms with no client change v.
